### 1-1. 로그인 없이 되는가? (pre-auth 여부)

**용어**
- **pre-auth (로그인 전 공격 가능):** 공유기 관리자 계정이나 로그인 세션 없이 요청만 보내서 일어나는 것.
- **post-auth (로그인 후):** 관리자(또는 로그인한 사용자)로 로그인해야 할 수 있는 것.
- **LAN 인접:** 공유기에 직접 연결된 같은 네트워크(유선·일반 Wi-Fi)에 있어야 닿는 것. 인터넷 쪽(WAN)에서는 닿지 않는 것.
- **L2 인접:** 같은 이더넷 구간(스위치·공유기에 직접 연결)에 있어야 하는 것. LAN 인접보다 조건이 더 까다롭습니다.

**WAN(인터넷 쪽)에서도 되나?** 이번에 확인한 범위에서는 **아니오(기본 설정 기준)** 입니다.
- UPnP 검색용 UDP 소켓은 모든 주소(`0.0.0.0`)에 열려 있지만 위에서 말한 LAN 대역 검사로 걸러집니다.
- UPnP 제어용 HTTP 소켓도 `0.0.0.0`에 열려 있지만(포트는 시작할 때 무작위로 정해짐), 기본 방화벽 규칙 파일(`default/configs/nfrule.json`)은 **INPUT 정책이 DROP**이고 WAN 쪽에서는 "기존 연결, 멀티캐스트, ICMP, DHCP"만 허용하며 UPnP 허용 규칙이 없습니다.
- **확인하지 못한 것:** 기기가 실제로 돌릴 때 추가되는 방화벽 규칙(원격 관리 등)과 이중 공유기·ISP 환경은 보지 못했습니다. 실제 인터넷 쪽에서 닿는지는 **직접 확인한 것이 아닙니다.**
- 따라서 OOB-02/03/04, DOS-01은 **"같은 네트워크 안의 누구나(로그인 없이)"** 가 대상인 취약점 후보이고, **"인터넷에서 누구나"는 아닌 것으로 보입니다.** 이 구분이 중요한 이유는 보고서에서 심각도를 다르게 평가하기 때문입니다.

## 3. 항목별 검증 방법

### 3-1. OOB-02 — UPnP 검색 응답이 정상보다 길게 나가는지

**무슨 일이 일어나나 (쉬운 설명)**
UPnP 기기를 찾을 때 PC가 공유기에 "너 누구니?"(M-SEARCH)라고 묻고, 공유기가 "나는 이런 기기야"라고 답합니다.
이때 질문에 들어 있는 `ST:` 글자가 길면, 공유기가 답장에 그 글자를 **두 번** 복사해 넣는데,
답장을 담는 상자(512바이트)보다 글자가 길어도 "만들려고 했던 길이" 그대로 전송합니다.
그러면 상자 밖(공유기 메모리)의 내용이 답장 끝에 같이 실려 나갑니다. 이게 사실이라면 메모리 일부가 새는 것입니다.

**실행**
```powershell
python ssdp01_real_router_test.py 192.168.0.1 | Tee-Object -FilePath 결과_OOB02.txt
```

**결과 읽는 법**
출력은 표 형태입니다.
```
ST suffix  ST total  reply bytes  verdict
        0        15          ...  normal (<= 511 bytes)
      100       115          ...  ...
```
- **정상 (재현 안 됨):** 모든 줄이 `normal (<= 511 bytes)`이고, 마지막에 `=== RESULT: no over-long reply. Not reproduced on this router. ===`
- **재현됨:** 어떤 줄에 `*** N bytes beyond the 512-byte buffer ***`이 나오고, 마지막에 `=== RESULT: reply longer than the 512-byte buffer -> OOB-02 reproduced ===` 와 함께 16진수 표(`+ 512  xx xx ...`)가 출력됩니다.
- **모든 줄이 `no reply`:** 공유기가 응답하지 않은 것입니다. → "6. 문제 해결"의 "응답이 없다"를 보세요.

**주의**: 재현되면 출력의 16진수 표에 공유기 메모리 일부(주소 등)가 들어 있을 수 있습니다. **인터넷에 올리지 마세요.**

**기기에 주는 영향:** 설정 변경 없음. UDP 패킷 몇 개를 보내고 응답을 읽을 뿐입니다.

### 3-2. OOB-03, OOB-04 — UPnP 이벤트 알림 (한 스크립트로 둘 다)

**무슨 일이 일어나나 (쉬운 설명)**
UPnP에는 "상태가 바뀌면 알려주세요"라고 등록(SUBSCRIBE)하는 기능이 있습니다. 등록할 때 "알림을 이 주소로 보내주세요(CALLBACK)"라고 알려줍니다.
- **OOB-03:** 그 주소의 **뒷부분(경로)을 아주 길게** 쓰면, 공유기가 알림 메시지를 만들 때 1024바이트 상자보다 길어져도 전체 길이로 보내서 상자 밖 메모리가 같이 실립니다.
- **OOB-04:** 주소에서 **포트 뒤에 `/`를 안 쓰면**, 공유기가 문자열 끝을 지나 메모리를 읽어서 알림 첫 줄에 이상한 바이트가 섞입니다.

공유기는 알림을 **등록한 PC의 IP**로만 보냅니다(다른 사람 PC로는 못 보냄). 그래서 이 테스트는 본인 PC에서만 일어납니다.

**실행**
```powershell
python evt01_real_router_test.py 192.168.0.1 | Tee-Object -FilePath 결과_OOB03_04.txt
```
(PC IP를 자동으로 못 찾으면 `python evt01_real_router_test.py 192.168.0.1 192.168.0.8`처럼 PC IP를 뒤에 붙이세요.)
Windows 방화벽 창이 뜨면 **개인 네트워크 허용**을 누르세요.

**결과 읽는 법**
출력이 두 부분입니다.

*Case A (OOB-03)* — 표가 나옵니다:
```
path len  subscribe reply     NOTIFY bytes  verdict
       0  HTTP/1.1 200 OK     ...           normal (<= 1023)
     400  ...                 ...           ...
```
- **정상:** 모든 줄이 `normal (<= 1023)`. 마지막에 `=== OOB-03: no NOTIFY longer than 1024 bytes on this router ===`
- **재현됨:** 어떤 줄에 `*** N bytes beyond the 1024-byte buffer ***`, 마지막에 `=== OOB-03 reproduced ... ===`와 16진수 표.
- `no NOTIFY received`가 나오면: 알림이 PC까지 오지 않은 것입니다(방화벽 차단이 가장 흔한 원인).

*Case B (OOB-04)* — 한 줄 판정입니다:
- `verdict: request line is clean (normal)` → 정상
- `verdict: *** request line contains unexpected bytes ... ***` → 재현됨 (출력된 `NOTIFY request line (bytes): ...`에 깨진 글자가 보임)
- 드물게 이 단계에서 공유기의 UPnP가 재시작되어 몇 초간 응답이 없을 수 있습니다.

**기기에 주는 영향:** 규칙/설정은 만들지 않습니다. 구독은 스크립트가 끝에 해지(UNSUBSCRIBE)하고, 안 지워져도 60초 뒤 자동 만료됩니다.

### 3-3. SBO-01 — NAS 계정 생성 시 관리 서버가 죽는지 (관리자 로그인 필요)

**무슨 일이 일어나나 (쉬운 설명)**
관리 페이지에서 USB 저장장치 공유용 "NAS 사용자"를 만들 때 "폴더 이름" 입력칸이 있습니다.
이 칸에 아주 긴 글자를 특정한 모양으로 넣으면, 관리 서버(`serviced`)가 자기 메모리 공간을 넘쳐 쓰다가 죽는다고 에뮬레이터에서 확인됐습니다.
**관리자로 로그인한 사람만** 할 수 있는 동작이라, 로그인 없이 쓸 수 있는 취약점은 아닙니다.

> ⚠️ **주의:** 성공하면 **관리 페이지가 몇 초~몇 분 안 열리거나, 공유기를 한 번 재부팅**해야 할 수 있습니다. 중요한 사용 중에는 하지 마세요. 설정 파일(플래시)에 쓰는 동작은 아니라서 영구 손상(브릭)은 예상하지 않습니다.

**준비: 로그인 쿠키 얻기**
1. 브라우저(크롬)로 공유기 관리 페이지에 **관리자로 로그인**합니다.
2. 키보드 `F12`를 눌러 개발자 도구를 엽니다 → 위쪽 탭에서 **Network(네트워크)** 선택.
3. 관리 페이지에서 아무 메뉴나 클릭해서 요청이 목록에 뜨게 합니다.
4. 목록에서 요청 하나를 클릭 → **Headers(헤더)** → **Request Headers(요청 헤더)** 안의 **`Cookie:`** 줄의 값 전체를 복사합니다. (길고 `=` 와 `;`가 섞인 글자입니다.)
5. 메모장에 임시로 붙여두세요. **이 쿠키는 비밀번호나 마찬가지이니 남에게 보여주지 마세요.**

**실행 (PowerShell에 한 줄로 붙여넣기)**
아래에서 `여기에_로그인_쿠키`를 복사한 쿠키로, `192.168.0.1`을 본인 공유기 IP로 바꾸세요 (3곳).
```powershell
$folder = ("A" * 400) + ":sbo01test_marker"; curl.exe -v -i -X POST http://192.168.0.1/cgi/service.cgi -H "Content-Type: application/json" -H "Referer: http://192.168.0.1/" -H "Cookie: 여기에_로그인_쿠키" --data "{\"method\":\"nas/user/add\",\"params\":{\"service\":\"smb\",\"enable\":true,\"id\":\"sbo01test\",\"password\":\"Test1234!\",\"folder\":\"$folder\",\"permission\":\"rw\"}}"
```

**결과 읽는 법**
- **재현된 것으로 볼 수 있는 신호:** 응답이 없이 **연결이 끊기거나**(`Empty reply from server`, `Recv failure`, `Connection reset` 같은 메시지), 시간이 한참 지나 타임아웃. 그리고 **요청 직후 관리 페이지를 새로고침했을 때 로그아웃되어 있거나 몇 초간 안 열리다가 복구됨**.
- **재현 안 됨:** 정상적인 JSON 응답이 옵니다(성공 또는 에러 메시지). 이 경우 `"A" * 400`의 `400`을 `600`, `800`으로 바꿔서 한두 번 더 시도해 보세요. 그래도 JSON 응답이 오면 "미재현"으로 기록합니다.
- 셸(SSH/텔넷) 접근이 있다면 더 확실합니다: 요청 **전후**에 `ps | grep serviced`의 PID가 바뀌었는지 확인하세요.

**끝난 뒤 정리**
관리 페이지의 "NAS 사용자 관리"에서 `sbo01test` 계정이 생겼으면 삭제하세요. 관리 페이지가 안 열리면 공유기 전원을 껐다 켜세요.

**알려둘 점:** 이 항목은 에뮬레이터에서 함수를 직접 호출해 확인한 것이라, **실제 웹 요청이 그 함수까지 도달할 때 길이가 어딘가에서 잘리는지**는 아직 확인되지 않았습니다. 그래서 실기기 결과가 특히 중요합니다.

### 3-4. DOS-01 — 인자 없는 UPnP 요청 하나로 UPnP가 죽는지

**무슨 일이 일어나나 (쉬운 설명)**
UPnP 요청(SOAP) 중 일부는 "시작 포트, 끝 포트" 같은 값이 꼭 들어가야 합니다.
이 값을 **빼고** 보내면 공유기 프로그램(`upnpd`)이 "값이 없음"을 확인하지 않고 쓰다가 죽는다고 에뮬레이터에서 확인됐습니다.
죽는 것은 **UPnP 기능뿐**이고, 인터넷·Wi-Fi는 그대로입니다.

> ⚠️ 성공하면 UPnP가 꺼진 채로 돌아오지 않을 수 있어서, **그때는 공유기를 재부팅**해야 합니다. 가장 마지막에 하세요. 업무용 기기에서는 하지 마세요.

**실행**
```powershell
python dos01_real_router_test.py 192.168.0.1 | Tee-Object -FilePath 결과_DOS01.txt
```

**결과 읽는 법**
스크립트가 순서대로 출력합니다.
```
Before:  (정상 요청의 응답 첫 줄)
Sending GetListOfPortMappings WITHOUT arguments...
Reply:   (응답 첫 줄 또는 연결 끊김)
After:   (정상 요청의 응답 첫 줄)
```
- **재현됨:** `After:`가 오류(`(error: ...)`)이거나 비어 있고 `=== service stopped answering right after the request -> DOS-01 likely reproduced. ... ===`. → 공유기를 재부팅해서 UPnP를 되살리세요.
- **재현 안 됨:** `After:`에 정상 응답이 오고 `=== UPnP still answers. ... ===`.
- 재시작되면 UPnP 포트 번호가 바뀔 수 있습니다(스크립트가 자동으로 다시 찾지는 않음).

## 6. 문제 해결

| 증상 | 원인과 해결 |
|---|---|
| `No UPnP router answered SSDP` 또는 모든 줄이 `no reply` | ① 공유기의 UPnP가 꺼져 있음 → 관리 페이지에서 켜기. ② PC가 공유기와 다른 대역(손님 Wi-Fi, VPN, 이중 공유기). ③ WSL에서 실행함 → PowerShell에서 실행. ④ PC에 네트워크 어댑터가 여러 개(가상 어댑터 등) → 다른 어댑터를 끄거나 유선만 연결 |
| `python`을 찾을 수 없음 | `py`로 바꿔 입력하거나 Python 설치 시 PATH 추가를 체크해 다시 설치 |
| OOB-03에서 `no NOTIFY received` | Windows 방화벽이 막음 → 허용 창에서 "개인 네트워크" 허용, 또는 방화벽 설정에서 Python 허용. 보안 프로그램이 막는 경우도 있음 |
| `curl.exe`가 없음 | Windows 10 1803 이전이면 [curl.se](https://curl.se/windows/)에서 설치 |
| SBO-01에서 JSON 에러 `unauthorized`/로그인 필요 | 쿠키가 만료됨. 다시 로그인해서 쿠키를 새로 복사 |
| SBO-01 후 관리 페이지가 안 열림 | 1~2분 기다린 뒤에도 안 되면 공유기 전원 재시작 |
| 결과가 매번 다름 | 정상입니다. 공유기 메모리 상태에 따라 달라질 수 있어서 같은 테스트를 **2~3번** 반복하고 결과를 모두 기록하세요 |

## 7. 하지 말 것

- 메인으로 쓰는 공유기, 다른 사람 소유 기기, 인터넷에서 접근되는 기기에서 하지 마세요. **본인 소유의 테스트 기기, 같은 로컬 네트워크에서만** 하세요.
- 스크립트를 수정해서 다른 대상(다른 IP)에 쓰지 마세요.
- 출력의 16진수 메모리 내용과 로그인 쿠키를 공개 장소에 올리지 마세요.
- 펌웨어 업그레이드 화면에서 "시작" 버튼을 누르지 마세요(FWVERIFY-01 선택 항목).
- 결과가 "재현 안 됨"이어도 다시 시도하느라 요청을 수십 번 반복하지 마세요. 2~3번이면 충분합니다.
