# ax3000ml v16.00.0 — 실기기 테스트 가이드 (초보자용, 3개 발견 통합)

이 문서는 2026-10-12~13 세션에서 찾은 **메모리 손상/설계 결함 3건**을
실제 공유기로 테스트하는 방법을 한곳에 모은 것입니다. 전부 코드를
끝까지 읽어서 정적으로 확인했고(Evidence 2), 그중 2개(OOB-01, SBO-01)는
QEMU 에뮬레이터 안에서 실제로 실행시켜서 크래시까지 눈으로 확인했습니다
(Evidence 3). 이 문서는 **그걸 여러분의 실제 기기로도 재현하는 법**입니다.

| ID | 한줄 요약 | 로그인 필요? | 위험도(기기 손상 관점) |
|---|---|---|---|
| **OOB-01** | UPnP로 공유기 메모리 일부가 새어나옴 | **불필요** (UPnP는 원래 로그인 없음) | 낮음 — 정보 유출만, 재부팅도 불필요 |
| **SBO-01** | NAS 계정 생성 시 특정 입력으로 관리 서버(serviced) 크래시 | **필요** (관리자 로그인) | 낮음~중간 — 플래시에 안 쓰는 크래시, 최악의 경우 재부팅 필요 |
| **FWVERIFY-01** | 펌웨어 업데이트가 암호 서명 검증을 안 함 | 조건부(아래 참고) | **있음 — 잘못하면 기기가 먹통(브릭)** |

**권장 순서: OOB-01 → SBO-01 → FWVERIFY-01.** 위험이 적은 것부터
해보시고, FWVERIFY-01은 안전 수칙을 꼭 지켜주세요.

## 0. 공통 준비물

- 공유기와 **같은 네트워크**(같은 와이파이 또는 LAN 케이블)에 연결된 PC 1대.
- Python 3 (OOB-01 테스트용). Windows는
  [python.org](https://www.python.org/downloads/)에서 설치.
- `curl` (SBO-01 테스트용). Windows 10/11은 기본 내장, 안 되면
  [curl.se](https://curl.se/windows/)에서 설치.
- FWVERIFY-01만 추가로: 이 모델의 **진짜 공식 펌웨어 파일**과
  헥스 에디터(Windows는 "HxD", Mac은 "Hex Fiend", 둘 다 무료).

## 1. OOB-01 — UPnP 메모리 유출 (로그인 불필요)

### 이게 뭔지

UPnP(게임기/토렌트 프로그램이 공유기한테 "이 포트 좀 열어주세요"라고
자동으로 부탁하는 기능)는 원래 로그인이 필요 없습니다. 포트를
열어달라고 할 때 같이 보내는 "설명(description)" 글자를 공유기 내부
저장 공간보다 길게 보내면, 나중에 그 포트 정보를 다시 물어볼 때
공유기가 **자기 메모리에 있던, 원래 안 보여줘야 할 내용까지 같이
섞어서 돌려줍니다.**

### 테스트 방법

1. PC를 공유기의 일반 와이파이/LAN에 연결합니다. (손님용 와이파이 X)
2. 터미널을 엽니다.
3. 아래 스크립트를 `oob01_real_router_test.py`로 저장합니다. (이미
   `emulation/OOB-01-upnpd/oob01_real_router_test.py`에 있는 파일과
   동일합니다 — 거기서 복사해도 됩니다.)
4. 실행:
   ```
   python3 oob01_real_router_test.py
   ```
5. 화면에 `[1/4]`~`[4/4]` 순서로 진행 상황이 나오고, 마지막에 공유기가
   돌려준 "설명" 값이 출력됩니다. 우리가 보낸 건 'A' 글자 200개뿐인데
   그보다 다른 내용이 섞여 나오면 — 메모리 유출이 재현된 겁니다.

스크립트 전체 코드와 상세 설명(정리 방법, 안 될 때 대처법 포함)은
`emulation/OOB-01-upnpd/GUIDE.md`와 `emulation/OOB-01-upnpd/
oob01_real_router_test.py`에 있습니다 — **그 파일을 그대로 이 폴더에
복사해서 쓰시면 됩니다.**

### 테스트 후 정리

포트 포워딩 규칙 1개(55123번)가 추가됩니다. 공유기 관리 페이지의
UPnP/포트포워딩 목록에서 지우거나, 120초 뒤 자동 만료를 기다리면 됩니다.

## 2. SBO-01 — NAS 계정 생성 시 관리 서버 크래시 (관리자 로그인 필요)

### 이게 뭔지

공유기의 "NAS 사용자 추가"(USB 외장하드를 samba/FTP로 공유할 때 쓰는
계정 생성 기능)에서, 공유 폴더 이름("folder" 값)을 특정 모양으로
길게 보내면 공유기의 관리 서버(`serviced`, 관리 웹페이지 전체를
담당하는 프로그램)가 **자기 자신의 메모리를 깨뜨리고 죽습니다.**

QEMU 에뮬레이터로 먼저 실행해봤는데, 보낸 글자가 그대로 레지스터에
찍히면서 크래시가 났습니다 — 진짜로 메모리가 깨진다는 뜻입니다.

### 안전성 참고

이건 **펌웨어(플래시 메모리)에 아무것도 쓰지 않는 크래시**입니다.
최악의 경우 관리 서버가 죽어서 **관리 웹페이지가 한동안 안 켜지거나,
공유기를 한 번 재부팅해야 할 수 있습니다.** 그 이상의 영구적인 손상
(브릭)은 예상되지 않습니다. 그래도 실제 운영 중인 공유기보다는
테스트용 기기에서 해보시길 권장합니다.

### 준비물

- 공유기 관리자 로그인 정보 (당연히 필요 — 이 취약점은 "로그인을
  건너뛸 수 있다"가 아니라 "로그인한 관리자가 평범한 기능을 쓰다가
  공유기 자체를 죽일 수 있다"는 내용입니다).

### 테스트 순서

1. 일반 브라우저로 `http://192.168.0.1/` (또는 여러분 공유기의 관리
   주소)에 접속해서 **정상적으로 관리자 로그인**합니다.
2. 로그인 상태에서 브라우저 개발자도구(F12) → **Network** 탭 →
   아무 요청이나 클릭 → **Request Headers**에서 `Cookie:` 값 전체를
   복사합니다.
3. 터미널을 열고, 아래 명령어에서 `여기에_로그인_쿠키`와
   `192.168.0.1`(여러분 공유기 IP)을 바꿔서 실행합니다.

**bash / WSL / Mac / Linux:**
```bash
FOLDER=$(python3 -c "print('A'*400 + ':sbo01test_marker')"); curl -i -X POST http://192.168.0.1/cgi/service.cgi -H "Content-Type: application/json" -H "Referer: http://192.168.0.1/" -H "Cookie: 여기에_로그인_쿠키" --data "{\"method\":\"nas/user/add\",\"params\":{\"service\":\"smb\",\"enable\":true,\"id\":\"sbo01test\",\"password\":\"Test1234!\",\"folder\":\"$FOLDER\",\"permission\":\"rw\"}}"
```

**Windows `cmd.exe`** (작은따옴표는 의미가 없어서 JSON이 깨지니,
아래처럼 큰따옴표+이스케이프로, 400자 문자열 생성까지 한 줄에 포함했으니
PowerShell에 그대로 붙여넣으세요):
```powershell
$folder = ("A" * 400) + ":sbo01test_marker"; curl.exe -v -i -X POST http://192.168.0.1/cgi/service.cgi -H "Content-Type: application/json" -H "Referer: http://192.168.0.1/" -H "Cookie: 여기에_로그인_쿠키" --data "{\"method\":\"nas/user/add\",\"params\":{\"service\":\"smb\",\"enable\":true,\"id\":\"sbo01test\",\"password\":\"Test1234!\",\"folder\":\"$folder\",\"permission\":\"rw\"}}"
```

### 결과 확인 방법

HTTP 응답만으로 보는 간단한 신호 (셸 접근 없어도 됨):
- **연결이 그냥 끊기거나(`curl: (56) Recv failure` 등) 응답 없이
  타임아웃**되면: 관리 서버가 요청 처리 중에 죽었을 가능성이 높습니다.
- **정상적인 JSON 에러/성공 응답이 온다면**: 이 특정 요청으로는 터지지
  않았다는 뜻입니다. (실기기의 스택 구조가 QEMU 테스트와 달라서
  `folder` 길이를 좀 더 늘려야 할 수도 있습니다 — 400을 600, 800으로
  올려서 다시 시도해보세요.)
- 요청을 보낸 **직후 관리 페이지를 새로고침**해보세요. 로그인이 풀려
  있거나 페이지가 몇 초간 안 뜨다가 복구된다면, 그 사이에 관리
  서버가 재시작된 것으로 볼 수 있습니다.

셸(SSH/텔넷) 접근이 있다면 더 확실하게 확인 가능합니다:
- 요청 보내기 **전**에 `ps | grep serviced`로 PID를 확인해두고,
  요청 보낸 **후** 다시 확인해서 PID가 바뀌었다면(재시작됐다면)
  크래시가 실제로 일어난 겁니다.
- `dmesg | tail` 또는 `/var/log` 쪽에서 `segfault`/`SIGSEGV` 관련
  로그가 남아있는지 확인하세요.

### 테스트 후 정리

요청이 크래시 전에 일부라도 처리됐다면 `sbo01test`라는 이름의 NAS
계정이 남아있을 수 있습니다. 관리 페이지의 "NAS 사용자 관리"에서
확인 후 삭제하시면 됩니다.

## 3. FWVERIFY-01 — 펌웨어 서명 검증 없음 (⚠️ 안전 수칙 필독)

### 이게 뭔지

공유기가 "새 펌웨어가 맞는지" 확인하는 과정은 **① CRC32 체크섬(위변조
방지용이 아니라 전송 오류만 잡는 용도), ② 제품 ID 평문 비교, ③ 버전
숫자 비교** 이 셋뿐입니다. 셋 다 비교 대상 값이 **공격자가 만드는
파일 안에 들어있는 값**이라, 암호학적으로 진짜인지 확인하는 절차가
전혀 없습니다. 게다가 이 검증은 **파일의 맨 앞 56바이트만** 읽습니다 —
그 뒤 수십 MB짜리 진짜 펌웨어 본문은 검증 과정에서 아예 열어보지도
않습니다.

### ⚠️ 반드시 먼저 읽으세요 — 이건 진짜로 기기를 먹통으로 만들 수 있습니다

이 항목만은 **"플래싱 직전 단계까지만" 가고 실제로 쓰기는 하지 않는
안전한 방법**으로 안내합니다. 아래 수칙을 반드시 지켜주세요.

- **원본 펌웨어 파일을 절대 직접 수정하지 마세요** — 항상 복사본으로
  작업하세요.
- **"확인/업그레이드 시작" 버튼은 절대 누르지 마세요.** 테스트 목적은
  "검증 단계를 통과하는지"를 보는 것이지 실제 설치가 아닙니다.
- 혹시 실수로 실제 업그레이드가 시작돼버렸다면, **절대 전원을 끄지
  말고** 끝까지 기다리세요 — 쓰기 도중 전원 차단이 브릭의 가장 흔한
  원인입니다.

### 준비물

- 이 공유기(또는 같은 시리즈) 모델의 **진짜 공식 펌웨어 파일**
  (제조사 홈페이지 다운로드 페이지).
- 헥스 에디터 (HxD, Hex Fiend 등).
- 공유기 관리자 로그인 정보.

### 테스트 순서

1. 공식 펌웨어 파일을 다운로드하고, **복사본을 만들어서 복사본으로만
   작업**합니다.
2. 헥스 에디터로 복사본을 엽니다.
3. 파일의 **맨 앞 56바이트(0x00~0x37번지)는 절대 건드리지 마세요.**
   그보다 훨씬 뒤쪽(예: 파일 크기의 중간쯤)으로 이동해서, 바이트
   몇 개를 아무 값으로나 덮어씁니다(예: 전부 `00`으로). 파일 크기가
   바뀌면 안 되니 "덮어쓰기"만 하세요.
4. 파일을 저장합니다.
5. 공유기 관리 페이지에 로그인한 뒤, "펌웨어 업그레이드" 메뉴에서
   이 수정된 복사본을 업로드합니다.
6. **"정상적인 펌웨어입니다, 진행하시겠습니까?" 확인 화면이 뜨는지만
   확인하고, 거기서 취소하거나 창을 닫으세요.**
   - 에러 없이 확인 화면이 뜬다면: **증명 완료입니다.** 파일 본문이
     바뀌었는데도 공유기가 "정상"이라고 판단했다는 뜻입니다.
   - "손상된 파일" 에러가 뜬다면: 바꾼 위치를 다르게 해서(예: 파일
     맨 끝 쪽) 다시 시도해보세요.
